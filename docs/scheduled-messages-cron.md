# Scheduled Messages – Cron Setup

Scheduled messages are sent by a cron job that processes due items (ideally every minute; on Railway at least every 5 minutes).

## Endpoint

- **URL:** `GET` or `POST` `/api/cron/send-scheduled-messages`
- **Auth:** Set `CRON_SECRET` in the backend env. Call the endpoint with either:
  - `Authorization: Bearer <CRON_SECRET>`, or
  - `x-cron-secret: <CRON_SECRET>`
- If `CRON_SECRET` is not set, the endpoint accepts requests without auth (suitable only for trusted networks).

---

## Creating `CRON_SECRET`

`CRON_SECRET` is not generated by Railway—you choose a random string and add it as an environment variable.

1. **Generate a secret** (pick one method):
   - Terminal: `openssl rand -hex 32`
   - Or use a password generator (e.g. 32+ random characters)
2. **Add it to your backend service in Railway:**
   - Open your **project** → select your **backend service** (the one running the API).
   - Go to the **Variables** tab.
   - Click **New Variable** (or **+ Variable**).
   - **Variable name:** `CRON_SECRET`
   - **Value:** paste the secret you generated.
   - Save. Redeploy the service if it’s already running so the new variable is picked up.

Use this **same value** whenever you call the cron endpoint (e.g. in a cron service or external cron).

---

## Where is the Cron Job section in Railway?

Railway doesn’t have a separate “Cron jobs” product. Cron is configured **per service**:

1. Open your **project** in the Railway dashboard.
2. Select a **service** (for this use case, a **separate** cron runner service—see below—not your main backend).
3. Go to the **Settings** tab (gear icon or “Settings” in the service menu).
4. Find **Cron Schedule**.
5. Enter a [crontab expression](https://docs.railway.com/cron-jobs#crontab-expressions) (e.g. `*/5 * * * *` for every 5 minutes).
6. Save. The service’s **start command** will then run on that schedule. The service must **exit** when the task is done (Railway does not stop it automatically).

**Important:** The shortest interval allowed is **5 minutes**. Schedules are in **UTC**.

## Option A: Cron service on Railway (every 5 minutes)

1. **Create a new service** in the same project (e.g. “scheduled-messages-cron”).
2. **Build/run:** use a minimal image that can run `curl` (e.g. `curlimages/curl` or a tiny Dockerfile that runs one command).
3. **Start command** should call your backend and then exit, e.g.  
   `curl -sf -X POST "$BACKEND_URL/api/cron/send-scheduled-messages" -H "x-cron-secret: $CRON_SECRET"`
4. **Variables** for this cron service:
   - `BACKEND_URL` = your backend’s public URL (e.g. `https://your-app.up.railway.app`)
   - `CRON_SECRET` = same value as in your backend service
5. **Settings** → **Cron Schedule:** `*/5 * * * *` (every 5 minutes).
6. Deploy. The service will start on schedule, run the `curl`, then exit.

---

## Option B: External cron (every minute)

To run **every minute**, use an external cron that sends an HTTP request:

- [cron-job.org](https://cron-job.org), [EasyCron](https://www.easycron.com), [Upstash QStash](https://upstash.com/qstash), or similar.
- Schedule: every minute.
- Request: `POST https://your-backend.up.railway.app/api/cron/send-scheduled-messages`
- Header: `x-cron-secret: <your CRON_SECRET>`
- Set `CRON_SECRET` only on your **backend** service (Variables tab), same value as in the external cron.

---

## Behaviour

- Selects rows in `scheduled_messages` with `status = 'pending'` and `scheduled_time <= NOW()` (UTC).
- For each row: sets status to `sending`, sends the message via Baileys (existing user connection), then sets `sent` and `sent_at` or `failed` and `error_message`.
- Failed sends are retried up to 3 times with exponential backoff (next run at now + 2^retryCount minutes).
- Requires the user’s WhatsApp session to be connected; if not, the send fails and is retried later.
